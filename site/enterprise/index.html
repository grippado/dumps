One company destination, from prompt to page.

The Enterprise recipe tells the skill to use the organization’s configured destination when the request involves company material. The team owns the server, CLI profile, identity policy and distribution of the skill.

01 Provision

Run a dumps host

Choose an internal name such as dumps.example.org. Configure the artifact origin, admin origin and SSH publishing route under your organization’s network and access policies.

02 Configure

Manage the publishing profile

Install the CLI and skill on an approved workstation. Provide a managed profile with the exact host and URL, and select it with DUMPS_CONFIG when people have multiple destinations.

03 Create

Ask the skill to publish internally

The skill follows the requested specialist and style, prepares the HTML, then uses the local CLI to publish over SSH and rsync. A hosted agent needs an organization-approved connector to reach a private service.

Protect the full path, including every artifact.

dumps serves static HTML. Your organization supplies the network boundary for confidential pages and the rules for who may publish them.

✓

Gate the artifact origin

Put SSO, VPN or private routing in front of all of DUMPS_URL, including the home page and each artifact.

✓

Limit publishing rights

Restrict the SSH route and publishing identity to approved people or managed agents. Keep org domains and credentials in private configuration.

✓

Choose a trust boundary

HTML pages share a browser origin. Use separate instances and origins for groups that must not trust each other’s artifacts.

✓

Keep external requests under policy

Leave analytics off and review fonts, scripts and other third-party requests before publishing internal material.

Two access boundaries

The admin listing and API are separate from the artifact host. DUMPS_AUTH configures supported admin identity checks; it does not protect static artifacts.

--hidden removes a dump from the home page. It does not require a login or make a public URL private.

Apply your SSO or VPN policy before requests reach the complete artifact origin.

Use Google Workspace with an access layer you already run.

Cloudflare Access can use Google Workspace as its identity provider today. Put separate Access applications in front of the complete artifact origin and the admin origin, then apply the organization's Workspace domain or group policy. For the admin API, configure DUMPS_AUTH=access so dumpsd verifies the Access token. For artifacts, Access protects every page at DUMPS_URL. Google sign-in is handled by Cloudflare Access in this setup; dumps does not validate Google tokens directly.

Proposed roadmap for deeper Enterprise support.

These are proposals, not shipped capabilities. The goal is to make artifact storage and identity fit into an organization's existing infrastructure while keeping the service self-hosted.

Proposed

S3-compatible artifact storage

Store published artifacts in a private object bucket and serve them through the organization's protected DUMPS_URL.

  • Preserve home, listing, archive, delete and rollback behavior.
  • Keep the bucket private behind an origin access layer and SSO or VPN.
  • Design writer coordination and recovery for object storage; do not assume filesystem rename or flock semantics.
  • Use scoped, short-lived cloud credentials instead of static access keys.
Proposed

Native Google Workspace access

Offer Google sign-in and organization policy as a first-class option for readers, publishers and admins, with separate permission boundaries.

  • Allow organization-controlled Workspace domains and, if feasible, groups.
  • Keep read access to artifacts separate from admin and publish permissions.
  • Validate identity and sessions server-side with explicit expiry and revocation behavior.
  • Keep Cloudflare Access with Google Workspace available as a current deployment option.

Proteja o caminho inteiro, inclusive cada artefato.

O dumps serve HTML estático. A organização fornece a fronteira de rede para páginas confidenciais e as regras de quem pode publicá-las.

✓

Proteja a origem dos artefatos

Aplique SSO, VPN ou rota privada em toda a DUMPS_URL, incluindo a home e cada artefato.

✓

Limite quem pode publicar

Restrinja a rota SSH e a identidade de publicação às pessoas ou agentes gerenciados. Mantenha domínios e credenciais da org em configuração privada.

✓

Defina a fronteira de confiança

As páginas HTML compartilham a mesma origem no browser. Use instâncias e origens separadas para grupos que não devem confiar nos artefatos uns dos outros.

✓

Controle pedidos externos

Deixe analytics desligado e revise fontes, scripts e outros pedidos a terceiros antes de publicar material interno.

Duas fronteiras de acesso

A listagem e a API do admin ficam separadas do host de artefatos. DUMPS_AUTH configura verificações de identidade compatíveis para o admin; não protege os artefatos estáticos.

--hidden tira um dump da home. Não exige login nem torna privado um endereço público.

Aplique a política de SSO ou VPN antes que os pedidos cheguem à origem inteira dos artefatos.

Use Google Workspace com uma camada de acesso que sua equipe já opera.

O Cloudflare Access pode usar Google Workspace como provedor de identidade hoje. Coloque aplicações Access separadas diante da origem completa dos artefatos e da origem do admin, depois aplique a política de domínio ou grupos do Workspace. Para a API do admin, configure DUMPS_AUTH=access para o dumpsd validar o token do Access. Para os artefatos, o Access protege cada página em DUMPS_URL. Nesse setup, o login Google é tratado pelo Cloudflare Access; o dumps não valida tokens Google diretamente.

Proposta de roadmap para ampliar o Enterprise.

Estas são propostas, ainda não recursos disponíveis. A meta é integrar armazenamento de artefatos e identidade à infraestrutura que a organização já opera, mantendo o serviço auto-hospedado.

Proposta

Armazenamento S3-compatible

Guardar os artefatos publicados num bucket privado e servi-los pela DUMPS_URL protegida pela organização.

  • Preservar home, listagem, arquivamento, remoção e rollback.
  • Manter o bucket privado atrás de uma camada de acesso à origem e de SSO ou VPN.
  • Projetar coordenação entre escritores e recuperação para object storage, sem pressupor rename de filesystem ou flock.
  • Usar credenciais de nuvem restritas e temporárias em vez de chaves estáticas.
Proposta

Acesso nativo com Google Workspace

Oferecer login Google e política da organização como opção de primeira classe para leitores, publicadores e admins, com permissões separadas.

  • Permitir domínios Workspace controlados pela organização e, se viável, grupos.
  • Separar leitura de artefatos das permissões de admin e publicação.
  • Validar identidade e sessões no servidor, com expiração e revogação explícitas.
  • Manter Cloudflare Access com Google Workspace como opção de deploy disponível hoje.
